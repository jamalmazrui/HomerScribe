# HomerScribe for Developers

What the program is made of, how the pieces fit together, and how to build it.

This is the companion to `ReadMe.md`, which is written for someone using
HomerScribe. Nothing here is needed in order to run it.

## What it is

One 64-bit Windows executable, written in C# against the .NET Framework 4.8, with
no DLL beside it and nothing to install for the program itself. 4.8 ships with
Windows 10 and 11, so the binary runs anywhere those do.

Roughly 3,000 lines in a single source file, `HomerScribe.cs`, in
`namespace Homer`. Style is Camel Type: Hungarian prefixes on typed identifiers,
lower camel case for methods and variables, double quotes, one-line simple
conditionals. `Camel_Type_C#.md` in this folder is the reference.

## The parts

### Written here

- **HomerScribe.cs** — everything: settings, the dialog, the pipeline, the
  prompts, the file handling.
- **Version.cs** — three lines holding `BuildVersion.Version`, generated by the
  build from `version.txt`. Never edited, never committed.

### Shared with the other Homer Tools

Copied unmodified from urlFido so that improvements to them keep porting between
tools. They compile into the same assembly, which is what keeps the result a
single file.

- **Lbc.cs** — layout-by-code dialogs. Builds the settings dialog without a
  designer, and supplies the Help button, the Escape and Enter behaviour, and the
  accessible names a screen reader reads.
- **Say.cs** — screen-reader announcements through UI Automation.
- **Inix.cs** — the ini codec, used for `HomerScribe.ini`.
- **Util.cs**, **Web.cs** — general helpers.

### Other programs, called not linked

None of these is linked into the executable. Each is a separate process, found at
run time beside the program, in `--ffmpeg-dir`, or on the PATH.

- **ffmpeg** does all the video and audio work: reading durations, finding
  silence, cutting frames, tiling montages, mixing and muxing, encoding mp3.
- **Ollama** serves the vision model over HTTP on `localhost:11434`. The program
  speaks to `/api/generate` and `/api/tags` and nothing else.
- **yt-dlp** fetches video from web addresses, and only then.
- **System.Speech**, part of the framework rather than a separate program, does
  the speaking. In process, straight to a memory stream at 48 kHz mono, so no
  temporary wave files are made and no process is spawned per description.

### Framework pieces worth knowing

- `JavaScriptSerializer` from `System.Web.Extensions` does the JSON. Not
  Newtonsoft: adding it would mean a DLL beside the executable, and nothing here
  needs what it does that the built-in one cannot. Its one trap is that a JSON
  array comes back as `ArrayList`, not `object[]`; everything goes through
  `toList` for that reason.
- `System.Speech` and the two UI Automation assemblies are **not** on the
  compiler's default reference path and must be given by full path, or the build
  fails with CS0006.

## How a description is made

For each moment, in order:

0. **Hear the film.** With Whisper installed, `whisper-cli` transcribes the sound
   track once into `transcript.json` in the working folder. The speech segments
   are inverted to give the quiet between the talking, and the transcript is kept
   so a resumed run never repeats it. Without Whisper the program falls back to
   the silence detection below.
1. **Find the moments.** Failing a transcript, ffmpeg's `silencedetect` reads the whole sound track
   once. Silences long enough and far enough apart become natural gaps. Because a
   scored film has almost none, `--every` places further moments at a fixed
   interval; those are marked, and the model is told its words will fall across
   the music and to say nothing unless the moment matters.
2. **Build a montage.** One ffmpeg call seeks to the moment, samples four frames
   across it, crops the bottom to hide burnt-in subtitles, scales, and tiles them
   two by two. A still-image model then sees time passing.
3. **Compare with the last one.** The montage is reduced to a 16 by 16 grey
   thumbprint. Barely changed means the moment is passed over in silence; changed
   a great deal means a new scene, and the model is asked to establish the place.
4. **Ask the model to look.** A POST to `/api/generate` with the montage as
   base64, the craft rules as the system message, and the per-moment material as
   the prompt: the context file, the last two descriptions, the names already
   used, the word budget.
5. **Ask the model to write.** A second call, same model, no image, turning what
   it saw into one spoken description. Following AutoAD-Zero: perceiving and
   being concise are different jobs.
6. **Check it.** Rejected and asked again if it repeats a recent description, if
   it judges rather than observes, or if it guesses at who someone is.
7. **Speak it.** `System.Speech` to a memory stream. If it overruns its slot the
   rate rises; then whole sentences are dropped; then trailing comma clauses,
   which leaves a sentence rather than a fragment; then the model is asked to say
   it again in fewer words. Words are never cut off the end. A description that
   runs a second long is better than one that stops mid-phrase, and a sentence
   opening with a place or a time is never cut back to that opening.
8. **Save.** The record is written after every single moment, so an interrupted
   run loses at most one.

At the end the spoken clips are laid onto a silent track at their exact sample
offsets, and ffmpeg mixes that with the film's own audio, ducking the film
underneath each description, and writes the result.

## Where things live

- The video's own folder: `described.mkv` (or `.mp3`) and `described.md`. Only
  what a person would open.
- `%LOCALAPPDATA%\HomerScribe\HomerScribe.ini` — the settings.
- `%LOCALAPPDATA%\HomerScribe\work\<video>-<tag>\` — the resume record, the
  caption file, the description track, the montages. The tag is a hash of the
  full input path, so two videos of the same name do not collide. On a finished
  run everything but the record is deleted.
- The run log goes with the results, or under application data when Log session
  is unticked.

Nothing is written beside the executable. Installed, that is
`C:\Program Files\HomerScribe`, which an ordinary user cannot write to — a
lesson learnt three times during development, once each for the log, the settings
and the working files.

## Building

### What you need

- **Roslyn**, from Visual Studio 2022 or the free Build Tools. The pre-Roslyn
  compiler under `Microsoft.NET\Framework64` is accepted as a fallback and will
  compile `HomerScribe.cs`, but the shared Homer modules use later language
  features.
- **The .NET Framework 4.8 Developer Pack**, for the reference assemblies.
  Without it `System.Speech.dll` and the UI Automation assemblies are not found.
- **Inno Setup 6**, to build the installer. Optional: without it the executable
  still builds.

### Building

    buildHomerScribe.cmd

    buildHomerScribe.cmd nobump

It writes `buildHomerScribe.log` beside itself and prints it at the end. What
it does, in order: increments `version.txt` unless told not to, generates
`Version.cs`, finds a compiler, finds the three full-path reference assemblies,
downloads ffmpeg and yt-dlp if they are missing or stale, compiles seven sources
into one assembly, and runs Inno Setup. The `.htm` documentation is built with
the `.md` and ships beside it, so the build generates nothing.

### Versioning

`version.txt` holds the version and nothing else. It is the single source: the
build reads it into `Version.cs`, and `HomerScribe_setup.iss` reads the same
file through `FileOpen` and `FileRead` and writes it into the version resource of
the setup. `tagRelease` then reads the FileVersion string back out of the built
setup and forms the tag.

No version literal appears in any other file, which is the point: a stale copy of
a file cannot rewind the number.

### Releasing

    buildHomerScribe.cmd
    git add -A && git commit -m "..."
    tagRelease

`createHomerScribeRepo.cmd` is the one-time bootstrap that creates the
repository. It, `tagRelease`, and their logs are in `.gitignore`; they are
maintainer tools and not part of the distribution.

### Traps

- The variable name `ProgramFiles(x86)` contains parentheses, and cmd scans a
  parenthesised block for its closing paren before expanding variables. The build
  copies it into a paren-free name before any block, and every search is a
  single-line `if not defined X if exist ... set` chain. The two install scripts
  do the same.
- A wildcard in the installer that matches nothing is a fatal error unless the
  line carries `skipifsourcedoesntexist`. Every source line except the executable
  has it.
- After Ollama is installed, it is not on the PATH of any console already open.
  `installModels.cmd` therefore looks for `ollama.exe` where it is put rather
  than asking `where`.
- `ffmpeg.exe` and `yt-dlp.exe` are downloaded at build time and are in
  `.gitignore`. They are far too large for a repository.
- A build cannot replace a running executable. The script renames it first as a
  test and says so plainly, because the compiler's own message for this —
  CS2012, "used by another process" — reads like a fault in the source.

## Changing the descriptions

Most of the quality lives in three places in `HomerScribe.cs`:

- `systemRules()` — the craft rules and the worked examples, sent as the system
  message. The examples do more work than the rules; a rule that is shown holds
  where one that is only stated does not.
- `promptFor()` — the per-moment material.
- `summarise()` — the second pass.

`asJudgmentWords` and `asHedgeWords` are the lists that trigger a retry, and
`asStripOpeners`, `asClauseTrims` and `asFilmTalk` clean the output afterwards.
All were grown from measuring real output rather than from imagination.

## Speed

On a machine with a capable graphics card a description takes about five seconds:
roughly half a second of ffmpeg, three or four seconds in the model across its
two passes, and a fifth of a second of speech.

Without one, the model runs on the processor and the same call takes two to three
minutes — forty times slower. A twenty minute video then takes hours. The program
reports its pace from the second description onward and says so when a run is
going to take hours, because otherwise it is indistinguishable from a hang.

## The prototype

`prototype\describeMovie.py` is the Python program this grew from, and it still
runs. It is the reference implementation, quicker to change when trying a new
prompt, and useful for checking whether a change in behaviour was deliberate. It
is behind the C# in several respects and is not needed to build or run
HomerScribe.

## What is not done

Ranked by what would improve descriptions most.

1. **A character bank.** The context file is a text-only version of AutoAD II's
   idea; the paper's version attaches face exemplars, which names characters far
   more reliably.
2. **A dialog that carries every setting.** It carries the ones named for it; the
   rest are command line only.
